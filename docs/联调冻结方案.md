# 联调冻结方案(提案,待四人确认)

目标:冻结一份共同接口与运行配置。冻结清单七项——实际部署位置、ROS2 与 Web 的桥接方式、
detect 消息字段、模型版本、时钟来源、手势功能范围,以及同一组真实样例消息核对。
本文档给出严晨越侧的两项决策提案(桥接方式、配置键名与同步)与我方真实样例,
其余项待对应成员提案。确认后回填《技术设计文档》第 11 章并升级 V0.2,再动代码。

## 一、提案 1:ROS2 与 Web 桥接方式(待定项 T1/T7)—— 方案 A:HTTP 下行桥

**现状**:上行已定——朱玉贺的 `dofbot_event_bridge`(Python,rclpy)订阅 `/task_event`,
按接口样例转 JSON 后 `POST` 记录服务 `/api/events`(已核实源码)。下行未定:
记录服务的 `RealControlAdapter`(严晨越)目前是占位。

**推荐方案 A:上行桥反向扩展下行**

```
看板 → 记录服务 → POST {control.url}/task_command → dofbot_event_bridge → ROS2 /task_command 服务
看板 ← 记录服务 ← 轮询 GET {control.url}/status   ← dofbot_event_bridge ← /control_status 话题
```

朱玉贺侧改动:bridge 增加下行 HTTP 端点(任务命令转 ROS2 服务调用 + 状态查询),
Python 实现,预计 50~100 行。严晨越侧改动:RealControlAdapter 实现为 HTTP 客户端
(httpx 已装,与 MockControlAdapter 同接口)。

**依据**:
1. 技术设计文档 T1 原文建议:「统一以 ROS2 为控制链路,Web 经后端服务桥接」——控制内部保持 ROS2,
   Web↔控制经桥接服务,方案 A 正是该建议;
2. 看板部署在普通 PC(技术设计 2.3,Windows)——备选方案 B(记录服务内嵌 rclpy 节点)
   需 Windows 上编译 ROS2 自定义消息包,成本高且脆弱;方案 A 看板机器零 ROS2 依赖;
3. 对"实际部署位置"未决项鲁棒:无论看板最终部署在哪台机器,HTTP 桥都成立,冻结后不返工;
4. 上行通道已存在且工作正常,下行是对称延伸,联调变量只多一个 `control.url`。

**需要朱玉贺确认的四个细节**:
1. bridge 增加下行端点(工作量小,见上);
2. 超时语义:ROS2 服务调用 5s 超时,超时返回 `accepted=false + error_code=CONTROL_TIMEOUT`,不挂起看板;
3. `request_id` 幂等:同一 request_id 重复下发返回相同结果,不重复执行;
4. 控制不可达:记录服务把设备状态置为 `fault` 并在看板明示,不静默。

**备选方案 B**(记录服务内嵌 ROS2 节点直接调 `/task_command`):仅当冻结会拍板
"记录服务部署在机器人同机 Linux"时才值得考虑;当前部署形态下不推荐。

## 二、提案 2:配置键名与同步(待定项)

**键名以看板 `/api/config` 为准**(`workspace.x_min`、`grab_height_mm`、`bins.red.x` 等),理由:
1. 技术设计 10.3:「统一进入配置并由看板参数页维护」——看板是配置唯一入口,控制模块是消费方;
2. 看板侧 JSON 已实现且有测试,朱玉贺侧 YAML 为内部格式,读取时做一层键名映射即可(改动量最小)。

**同步机制**(搭方案 A 同一座下行桥,不另开通道):
- 看板保存 → 记录服务写库 → 下发 `{control.url}/config` → 控制模块写 YAML;
- 热加载:控制模块在每次 `start` 自检时重读配置,改完下次启动即生效,无需重启节点;
  运动参数运动中已被 409 锁住(契约 6.6),下发时机天然安全;
- 失败语义:保存优先于下发——控制不可达时配置照样保存,看板提示
  「已保存,控制模块未确认接收」,连接恢复后补发。

**注意**:`confidence_threshold` 的消费者是张鹏源的检测服务,不是控制模块,
该字段的同步通道与张鹏源单独确认(建议他检测服务暴露 HTTP 参数端点或读同一配置端点),
不混入控制模块的下发通道。

## 四、我方真实样例(2026-11-11 运行记录服务真实抓取,非手写)

以下 JSON 由 `server/` 真实代码运行产生,冻结会上请与朱玉贺桥接的实际输出逐字核对。

### 1. task_event 上报(朱玉贺 → 记录服务)

请求(POST /api/events,事件数组):

```json
[
  {
    "event_id": "SAMPLE-T001-queued",
    "task_id": "SAMPLE-T001",
    "occurred_at_ms": 1763000000000,
    "status": "queued",
    "color": "red",
    "x_mm": 12.5,
    "y_mm": -34.0,
    "z_mm": 40.0,
    "started_at_ms": null,
    "finished_at_ms": null,
    "error_code": null,
    "mode": "real",
    "result_basis": "none"
  }
]
```

响应:首次 `{"inserted": 1}`;相同 event_id 重复上报 `{"inserted": 0}`(幂等)。

### 2. task_command(看板 → 记录服务 → 桥接 → 控制)

请求 / 响应(实测:start 返回时状态为 idle,自检完成约 1.4s 后转 running):

```json
{ "request_id": "sample-1", "action": "start" }
→ { "accepted": true, "state": "idle", "error_code": null }

{ "request_id": "sample-2", "action": "stop" }
→ { "accepted": true, "state": "stopping", "error_code": null }
```

### 3. 状态查询(GET /api/state)

```json
{
  "state": "running",
  "self_check": {
    "running": false,
    "items": [
      { "name": "舵机位置", "status": "ok" },
      { "name": "RGB 灯", "status": "ok" },
      { "name": "蜂鸣器", "status": "ok" }
    ],
    "checked_at_ms": 1794373053599
  },
  "demo": null
}
```

### 4. 配置(GET /api/config —— 键名以此为准)

```json
{
  "confidence_threshold": 0.5,
  "workspace": { "x_min": -60, "x_max": 60, "y_min": -60, "y_max": 60 },
  "grab_height_mm": 40,
  "bins": {
    "red": { "x": 160, "y": 90 },
    "yellow": { "x": 160, "y": -90 },
    "blue": { "x": -160, "y": 90 },
```

### 5. 枚举校验行为(非法值 422)

`status: "success"`(契约无此值)上报返回 422,响应 detail 明确列出合法值:

```json
{
  "detail": [
    {
      "type": "literal_error",
      "loc": ["body", 0, "status"],
      "msg": "Input should be 'queued', 'running', 'succeeded', 'failed', 'skipped' or 'stopped'",
      "input": "success",
      "ctx": { "expected": "'queued', 'running', 'succeeded', 'failed', 'skipped' or 'stopped'" }
    }
  ]
}
```
